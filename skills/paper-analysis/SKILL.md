# paper-analysis

論文1本を深く理解するためのレポートを作る。レポートの価値は「論文に何が書いてあるか」を正確に、根拠の場所つきで示すことにある。読み手はレポートを入口にして原文に戻れることを期待しているため、論文に書かれていないこと（分析者の感想、利用者の研究への示唆、論文の外の知識による評価）は書かない。

## 全体の流れ

1. 論文を手に入れ、本文をテキストにする
2. 根拠メモを作る（論文から事実を、場所と原文つきで抜き出す）
3. 根拠メモだけを材料に、レポートの原稿（Markdown）を書く
4. 原稿を点検する（原文の引用の照合、数値の照合）
5. 日本語を校正する（予算の上限つき）
6. HTMLにしてArtifactとして公開する

作業用のファイルは、作業用の場所（スクラッチパッドがあればその中）に `paper-analysis-<短い名前>/` を作ってまとめる。ダウンロードした論文は、その下の `source/` という空のフォルダーに置く。

## 1. 論文を手に入れる

入力の種類ごとの手順は `references/sources.md` にある。要点だけ書く。

- PDFのファイル：`pdftotext -layout <PDF> <作業フォルダー>/paper.txt` でテキストにする。`pdftotext` がなければ、Readツールでページを指定して読む（1回に20ページまで）
- arXiv：`https://arxiv.org/pdf/<ID>` からPDFを取る。版（v1、v2…）の指定があればそれに従い、なければ最新版を使い、使った版をレポートに書く
- DOIや出版社のURL：まずオープンアクセスの版を探す。全文が手に入らないときは、要旨だけで分析せず、利用者にPDFを求める。要旨だけでは「深い理解」という目的を果たせないため

テキストにしたら、ページの区切り（`\f`）が残っていることを確かめる。ページ番号を根拠に使うためである。

## 2. 根拠メモを作る

本文を最初から最後まで読み、次の項目を `<作業フォルダー>/evidence.md` に抜き出す。レポートはこのメモだけを材料に書く。読みながら直接レポートを書くと、記憶で補ったことや論文の外の知識が混ざりやすいためである。

- 研究の問い、目的、貢献として著者が挙げていること
- 手法、データ、実験の設定（数値、条件、比較対象）
- 結果（表や図の数値。単位と条件を落とさない）
- 著者が述べた解釈、限界、今後の課題
- 用語の定義（論文の中で定義されているもの）

1項目につき、次の形で書く。

```text
- [p.5 §3.2] 提案手法は、検証データで正解率91.2%を達成した
  原文："Our method achieves 91.2% accuracy on the validation set"
```

- 場所は、ページ（`p.`）と節（`§`）、図表（`図2`、`表3`）で示す。ページ番号は論文に印刷されたものではなく、PDFの何ページ目かを使う（印刷されていない論文もあるため）。印刷されたページ番号を使った場合はレポートの書誌情報にその旨を書く
- 原文は、論文から一字一句そのまま写す。後で機械的に照合するため、言い換えや省略をしない。長いときは、主張の中心になる一文だけを写す
- 図の中の数値など、テキストにならない情報は、Readツールで該当ページを画像として見て拾う。その場合は原文の行に `（図から読み取り）` と書く

## 3. 原稿を書く

`references/report-template.md` の構成で、`<作業フォルダー>/report.md` に日本語の原稿を書く。

### 書いてよいこと、書かないこと

| 書く | 書かない |
| --- | --- |
| 論文に書かれた事実、数値、主張 | 分析者の評価（「画期的」「説得力がある」など） |
| 著者自身が述べた限界と課題 | 論文が述べていない弱点の指摘 |
| 論文の中の定義に基づく用語の説明 | 利用者の研究への示唆や応用の提案 |
| 論文に書かれていないことの明示（「データの規模は記載がない」） | 論文の外の知識による補足や推測 |

最後の行が大事である。理解のために論文の外の説明（一般的な用語の意味など）がどうしても要るときは、用語集の中か直後にだけ書き、`論文外の補足：` と明示する（書き方は `references/report-template.md` の例）。本文の節には混ぜない。

### 根拠の示し方

- 事実を述べる文には、文末に根拠の場所を `〔p.5 §3.2〕` の形で付ける。複数あれば `〔p.5 §3.2、表3〕` とする
- 主張の中心になる箇所には、根拠メモの原文を引用として添える（`> 原文："..."`）。全部の文に付けると読みにくいため、各節で2〜4か所に絞る
- 著者の主張（「〜と著者は述べている」）と、実験で示された結果（「表3では〜」）を書き分ける。読み手が、どこまでが証拠に裏づけられているかを判断できるようにするためである

### 文章

- 読み手は、その分野をある程度知っているが、この論文はまだ読んでいない人を想定する
- 英語の専門用語は、初出で `訳語（原語）` の形にする。定着した訳語がなければ原語のまま書く
- 数値は原文のとおりに書き、丸めない。単位と条件（どのデータで、何と比べて）を必ず添える

## 4. 原稿を点検する

### 原文の照合（機械）

```bash
python3 <スキルのディレクトリ>/scripts/check_quotes.py <作業フォルダー>/report.md <作業フォルダー>/paper.txt
```

`<スキルのディレクトリ>` は、このSKILL.mdがあるディレクトリの絶対パスである。原稿の `原文："..."` が本文に見つからなければ、行番号つきで報告する。見つからない引用は、写し間違いか、論文にない文である。`paper.txt` を検索して正しい文に直すか、引用を消す。`（図から読み取り）` の行は照合の対象外になる。

### 数値と主張の照合（読んで確かめる）

原稿の数値を一つずつ、根拠の場所の本文と見比べる。特に次の取り違えが起きやすい。

- 表の行と列（どの手法の、どのデータセットの値か）
- 比較の向き（「〜より高い」「〜%改善」の基準）
- 著者の主張と結果の混同（著者が「示唆される」と書いたことを「示した」と書いていないか）

照合の途中で、論文の中の記述どうしの食い違い（要旨や本文の数値と表の数値が違うなど）に気づいたら、原稿の「論文の中の食い違い」の節に、両方の場所つきで書く。論文の中の事実どうしの比較なので、評価には当たらない。

直したところは、根拠メモも合わせて直す。

## 5. 日本語を校正する

docs-rulesスキルのルールで原稿を校正する。docs-rulesのルールを全部読み込むと数万トークンを使うため、ここでは予算の上限を決めて行う。手順と上限の変え方は `references/proofreading.md` にある。既定の上限は次のとおり。

| 項目 | 既定値 |
| --- | --- |
| 機械の採点（`score.mjs`） | 1回。LLMのトークンをほとんど使わない |
| 書き直しに渡す違反 | 最大30件 |
| 書き直しの回数 | 1回 |
| AIによる評価（docs-rulesの`evaluate.md`） | 行わない。利用者が「しっかり校正して」などと頼んだときだけ、費用の上限つきで行う |

docs-rulesが入っていない環境では、校正を飛ばし、そのことを最後の報告に書く。

校正では、事実の内容を変えない。言い回しだけを直し、数値、根拠の場所、`原文："..."` の中身には触れない。校正の後にもう一度 `check_quotes.py` を実行し、引用が壊れていないことを確かめる。

## 6. HTMLにして公開する

```bash
python3 <スキルのディレクトリ>/scripts/render_html.py <作業フォルダー>/report.md <出力先>.html
```

デジタル庁デザインシステム（DADS）のトークンに沿ったHTMLを、外部のファイルなしの1ファイルで作る。ライトとダークの両方に対応し、目次、根拠の場所の強調、引用の表示を整える。デザインの出典と変え方は `references/design.md` にある。

- Artifactツールがある環境：作ったHTMLをArtifactとして公開し、リンクを利用者に示す。`icon` は `book` にする
- Artifactツールがない環境：HTMLのファイルのパスを示す

HTMLを手で書き換えない。直したいところがあれば `report.md` を直して作り直す。原稿とHTMLの中身がずれないようにするためである。

## 最後の報告

チャットには、レポートの中身を繰り返さず、次だけを短く書く。

```text
分析レポート：<ArtifactのリンクかHTMLのパス>
対象：<著者>（<年>）"<タイトル>"（<arXiv ID、DOIなど>）
点検：引用の照合 12件すべて一致、数値の照合 済み
校正：機械の採点で違反18件 → 書き直し1回で残り2件（AIによる評価は行っていない）
```

全文が手に入らなかった、図が読めなかったなど、分析の範囲を狭めた事情があれば、ここに書く。
